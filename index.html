3. Origin & CORS คืออะไร? (ทำไมตอนแรกเว็บดึง API ไม่ได้?)

  • Origin (ต้นทางของเว็บ) ประกอบด้วย 3 อย่างรวมกัน: Scheme (โปรโตคอล) + Host (ชื่อโดเมน) + Port (เลขพอร์ต)
  • ตัวอย่าง: หน้าเว็บอยู่ที่ http://lvm68174.sit.kmutt.ac.th:8174 แต่ไปดึงข้อมูลนักเรียนจาก http://lvm68174.sit.kmutt.ac.th:3174/api/students ──► แม้จะอยู่เครื่องเดียวกัน แต่ เลขพอร์ตต่างกัน (8174 vs 3174) จึงถือเป็นคนละ Origin (Cross-Origin)!
  • ความเข้าใจผิดที่ออกสอบบ่อยมาก: เมื่อเกิด CORS Error (Failed to fetch) หลายคนคิดว่าเซิร์ฟเวอร์ API ไม่ยอมตอบ แต่จริงๆ แล้วถ้าเปิดแท็บ Network ดู จะเห็นว่า API ตอบ 200 OK กลับมาแล้ว! แต่ Web Browser เป็นคนบล็อก ไม่ให้โค้ด JavaScript อ่านข้อมูลนั้น เพราะใน Response Header ไม่มีป้ายอนุญาตที่ชื่อว่า Access-Control-Allow-Origin
  • วิธีแก้ที่แท้จริง (ทางสาย Deployment): แทนที่จะเปิดพอร์ต API ทิ้งไว้ข้างนอกแล้วตั้ง CORS เราเอา Nginx Reverse Proxy มาบังข้างหน้า ให้ทั้งหน้าเว็บ (/school/) และ API (/school/api/) เข้าผ่านพอร์ตเดียวกัน (พอร์ต 80/443) ──► กลายเป็น Same Origin (ต้นทางเดียวกัน) ทันที ไม่ต้องพึ่ง CORS อีกต่อไป และปิดพอร์ต API จากโลกภายนอกได้เลย!

  • วิธีที่ถูกต้อง: ใช้คำสั่ง rsync คัดลอกเฉพาะไฟล์ใน /srv/school/frontend/ ไปไว้ที่ /var/www/school/:
คำสั่ง rsync สำหรับ Deploy Frontend (Class 5)
sudo mkdir -p /var/www/school
sudo rsync -a --chmod=D755,F644 --delete --exclude config.js /srv/school/frontend/ /var/www/school/
  • -a (Archive): คัดลอกแบบรักษาโครงสร้างโฟลเดอร์และเวลาแก้ไขไฟล์
  • --chmod=D755,F644: บังคับสิทธิ์ให้โฟลเดอร์เป็น 755 (rwxr-xr-x) และไฟล์เป็น 644 (rw-r--r--) เพื่อไม่ให้มีสิทธิ์เขียน (w) เกินจำเป็น
  • --delete: ถ้าไฟล์ไหนถูกลบออกจากต้นทาง (/srv/school/frontend/) ให้ลบออกจากปลายทาง (/var/www/school/) ด้วย
  • --exclude config.js: สำคัญมาก! ไม่คัดลอกไฟล์ config.js ไปทับไฟล์ที่เราตั้งค่าไว้แล้วที่ปลายทาง
  • สังเกตเครื่องหมาย / หลัง frontend/: ใน rsync การใส่ / ปิดท้ายต้นทาง หมายถึง "เอาเฉพาะไส้ในของโฟลเดอร์ frontend ไปวาง" (ต่างจาก docker cp ใน Class 6 ที่ต้องใช้ /.!)

3. Forward Proxy vs. Reverse Proxy ต่างกันอย่างไร?

🧑‍💻 Forward Proxy (ตัวแทนฝั่งผู้ใช้ / Client)

ตั้งอยู่หน้าฝั่งผู้ใช้ (เช่น Proxy ขององค์กร หรือ VPN) คอยเป็นตัวแทนออกไปดึงเว็บข้างนอกให้ผู้ใช้ โดย เซิร์ฟเวอร์ปลายทางจะไม่รู้ว่าผู้ใช้ตัวจริงคือใคร (เห็นแต่ IP ของ Forward Proxy)

🏢 Reverse Proxy (ตัวแทนฝั่งเซิร์ฟเวอร์ / Server)

ตั้งอยู่หน้าเซิร์ฟเวอร์ของเรา (คือ Nginx ที่เราทำในวิชานี้!) คอยรับคำขอจากผู้ใช้ที่เข้าพอร์ต 80/443 แล้วส่งต่อ (Proxy) ไปยัง Backend ข้างหลัง โดย ผู้ใช้ภายนอกไม่รู้เลยว่าข้างหลังมีกี่เซิร์ฟเวอร์หรือรันอยู่ที่พอร์ตอะไร

4. กฎเหล็ก proxy_pass มี / ปิดท้าย vs. ไม่มี / ปิดท้าย (ออกสอบ 1000%!)

เวลาเขียนบล็อก location คู่กับ proxy_pass ใน Nginx การใส่หรือไม่ใส่ Path/Slash (/) หลังเลขพอร์ต จะเปลี่ยน URL ที่ส่งไปหาเซิร์ฟเวอร์ข้างหลังทันที:

รูปแบบการเขียนใน Nginx มี Path / / หลัง Host:Port หรือไม่? เมื่อผู้ใช้เรียก /school/api/students Nginx จะส่งอะไรไปข้างหลัง? ใช้เมื่อไหร่?
location /school/api/ {
  proxy_pass http://127.0.0.1:3174/api/;
} 		มี URI ต่อท้าย (/api/) ตัดคำที่ตรงกับ location (/school/api/) ออก แล้วเอา /api/ ไปแปะแทน ──► ส่งไปเป็น /api/students ใช้ที่ Proxy ตัวสุดท้ายก่อนถึงตัวแอป (เพราะตัวแอป Node.js รู้จักแค่ /api/students ไม่รู้จักคำว่า /school)
location /school/ {
  proxy_pass http://web/;
} 		มี / ปิดท้าย ตัดคำว่า /school/ ออก แล้วแทนด้วย / ──► ถ้าร้องขอ /school/app.js จะส่งไปเป็น /app.js ใช้เมื่อส่งต่อให้คอนเทนเนอร์ Frontend (เพราะไฟล์ในคอนเทนเนอร์วางอยู่ที่ราก /usr/share/nginx/html/app.js)
location /school/ {
  proxy_pass https://127.0.0.2:8443;
} 		ไม่มี / ปิดท้าย! ไม่ตัดอะไรเลย! ส่ง Path เดิมไปทั้งดุ้น ──► ส่งไปเป็น /school/api/students หรือ /school/ เหมือนเดิมเป๊ะ ใช้ใน Class 10 (Outer Proxy บน Host ส่งเข้า Inner Stack Proxy) เพื่อให้ Stack Proxy ข้างในเป็นคนแยกเองว่าอันไหนไป web อันไหนไป api!

5. ทำไมต้องใส่ proxy_set_header ทั้ง 4 บรรทัดเสมอ?

ตามค่าเริ่มต้น เมื่อ Nginx ส่งคำขอต่อไปยังเซิร์ฟเวอร์ข้างหลัง (Upstream) มันจะสร้าง HTTP Request ใหม่โดยใส่ Host เป็น 127.0.0.1:3174 และต้นทาง IP เป็น 127.0.0.1 ทำให้เซิร์ฟเวอร์ข้างหลังไม่รู้ข้อมูลจริงของผู้ใช้เลย เราจึงต้องแนบ Header 4 บรรทัดนี้ไปด้วยเสมอ:

4 บรรทัดศักดิ์สิทธิ์ใน location ที่ทำ proxy_pass
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
  • Host $host: บอกชื่อโดเมนที่ผู้ใช้พิมพ์เข้ามาจริงๆ (เช่น lvm68174.sit.kmutt.ac.th) — ถ้าลืมใส่ เวลาทำ Redirect ข้างใน มันจะเด้งไปหา https://127.0.0.2/... ซึ่งพังทันที!
  • X-Real-IP $remote_addr: ส่ง IP จริงของผู้ใช้ที่ต่อเข้ามาหา Nginx ตัวนี้
  • X-Forwarded-For $proxy_add_x_forwarded_for: รายชื่อ IP ของผู้ส่งต่อทุกทอด (กรณีผ่าน Proxy หลายชั้น)
  • X-Forwarded-Proto $scheme: บอกว่าผู้ใช้เข้าผ่านโปรโตคอลอะไร (http หรือ https)

6. ระบบกุญแจ 2 ชั้น (Two Independent Locks) เพื่อปิดประตูหลังบ้าน

  1. กุญแจชั้นใน (Inner Lock — การผูก IP / Binding): ตั้งให้ API รับฟังเฉพาะที่ 127.0.0.1 (หรือผูกพอร์ต Docker ไว้ที่ 127.0.0.2) ต่อให้ลืมเปิด Firewall คนนอกก็ส่งแพ็กเก็ตเข้า Loopback ไม่ได้
  2. กุญแจชั้นนอก (Outer Lock — Firewall UFW): ปิดพอร์ต API บน UFW ด้วยคำสั่ง sudo ufw delete allow 3174/tcp

7. การสร้าง Self-Signed TLS Certificate และทำไมต้องใช้ HTTP 308?

คำสั่งสร้างใบรับรอง SSL/TLS (Self-Signed Certificate) อายุ 365 วัน
sudo mkdir -p /etc/ssl/int134
sudo openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout /etc/ssl/int134/vm.key \
  -out /etc/ssl/int134/vm.crt \
  -subj "/CN=$(hostname -f)" \
  -addext "subjectAltName=DNS:$(hostname -f),DNS:$(hostname)"
sudo chmod 600 /etc/ssl/int134/vm.key
  • -x509: สร้างใบรับรองที่เซ็นรับรองตัวเอง (Self-signed certificate) แทนที่จะสร้างแค่ใบคำขอ (CSR)
  • -nodes (ย่อมาจาก no DES encryption): ไม่ต้องตั้งรหัสผ่านล็อกไฟล์ Private Key เพราะถ้าตั้งรหัสผ่านไว้ เวลาเครื่องรีบูตแล้ว Nginx สตาร์ทขึ้นมาเอง มันจะค้างรอให้คนพิมพ์รหัสผ่าน!
  • -newkey rsa:2048 -days 365: สร้างกุญแจ RSA ขนาด 2048 บิต มีอายุ 365 วัน
  • chmod 600 vm.key: ไฟล์กุญแจส่วนตัว (.key) ต้องให้เฉพาะเจ้าของ (root) อ่านได้เท่านั้น
  • ทำไมใช้ return 308 https://$host$request_uri; แทนที่จะใช้ 301 หรือ 302?
    • ในอดีต รหัส 301 (Moved Permanently) และ 302 (Found) มีข้อเสียคือ เบราว์เซอร์มักจะเปลี่ยนคำขอจาก POST ให้กลายเป็น GET และทิ้งข้อมูลใน Body ตอนเปลี่ยนหน้า!
    • ส่วน 308 Permanent Redirect (และ 307 Temporary Redirect) บังคับว่า ห้ามเปลี่ยน HTTP Method เด็ดขาด (ถ้าส่ง POST มา พอเด้งไป HTTPS ก็ยังเป็น POST พร้อมข้อมูลครบถ้วน)

🐳 Class 6: Introduction to Container & Docker Architecture พื้นฐานสำคัญ

1. Virtual Machine (VM) vs. Container ต่างกันอย่างไร?

🖥️ Virtual Machine (VM)

จำลองตั้งแต่ระดับ Hardware ผ่าน Hypervisor ทำให้แต่ละ VM ต้องแบก Guest OS Kernel ทั้งก้อน ของตัวเอง กินแรมเป็นกิกะไบต์ (GB) และใช้เวลาบูตเป็นนาที

📦 Container (Docker)

จำลองในระดับ OS โดย แชร์ Linux Kernel ร่วมกับเครื่อง Host แต่กั้นห้องแยก Process (ด้วย namespaces) และจำกัดทรัพยากร (ด้วย cgroups) ทำให้ขนาดเล็กมาก (หลัก MB) และสตาร์ทขึ้นในเสี้ยววินาที!

2. 4 คำศัพท์หลักของ Docker และระบบแผ่นใสซ้อนทับกัน (Union File System / overlay2)

  • Docker Image: แม่พิมพ์ที่ประกอบด้วย Read-Only Layers (ชั้นข้อมูลที่อ่านได้อย่างเดียว แก้ไขไม่ได้) ซ้อนทับกัน เปรียบเหมือน Class หรือไฟล์โปรแกรมที่ยังไม่รัน
  • Docker Container: เมื่อสั่ง docker run Docker จะนำ Image มาวาง แล้วแปะ ชั้นบางๆ ที่เขียนทับได้ (Thin Read-Write Layer) ไว้ด้านบนสุด!
    • ถ้ามีการสร้างหรือแก้ไขไฟล์ขณะรัน จะถูกเขียนลงใน Read-Write Layer นี้เท่านั้น (เทคนิค Copy-on-Write)
    • ถ้าลบไฟล์ที่มีอยู่ในชั้น Image ข้างล่าง เนื่องจากชั้น Image เป็น Read-Only ลบไม่ได้ Docker จึงวางไฟล์พิเศษที่ชื่อว่า Whiteout file (.wh.<ชื่อไฟล์>) ไว้ที่ชั้นบน เพื่อบังไม่ให้มองเห็นไฟล์ข้างล่าง!
    • เมื่อสั่ง docker rm ลบคอนเทนเนอร์ ชั้น Read-Write Layer จะหายไปทั้งหมด!

4. ทำไมใน entrypoint.sh ต้องใช้ exec "$@" แทนที่จะเขียน "$@" เฉยๆ?

❌ ถ้าบรรทัดสุดท้ายเขียนแค่ "$@" (ไม่มี exec)

ตัวเชลล์ /bin/sh ./entrypoint.sh จะนั่งเป็น PID 1 แล้วแตกโปรเซสลูกให้ node server.js เป็น PID อื่น
เมื่อเราสั่ง docker stop school-api Docker จะส่งสัญญาณ SIGTERM ไปบอก PID 1 (/bin/sh) ให้ปิดตัว แต่ /bin/sh ไม่ยอมส่งสัญญาณต่อให้ลูก! ทำให้คอนเทนเนอร์ค้างอยู่ถึง 10 วินาทีเต็ม จนหมดเวลา แล้วถูก Docker ทุบด้วย SIGKILL!

✅ ถ้าบรรทัดสุดท้ายเขียน exec "$@"

คำสั่ง exec จะสั่งให้เชลล์ สละร่างตัวเองแล้วเอาคำสั่งใน "$@" (คือ node server.js) ขึ้นมาแทนที่เป็น PID 1 โดยตรง!
เมื่อสั่ง docker stop school-api ตัว node server.js จึงได้รับ SIGTERM ทันที และปิดตัวเองอย่างนุ่มนวลภายใน ไม่ถึง 1 วินาที (0 วินาที)!

ไฟล์ /srv/school/backend/entrypoint.sh (ต้องรัน chmod +x entrypoint.sh ด้วย!)
#!/bin/sh
# ตรวจสอบว่ามีไฟล์ถูก mount เข้ามาที่ /app/.env และมีขนาดมากกว่า 0 ไบต์ (! -s แปลว่าไม่มีไฟล์ หรือไฟล์ขนาด 0 ไบต์)
if [ ! -s /app/.env ]; then
  echo "entrypoint: no configuration mounted at /app/.env - refusing to start" >&2
  exit 1
fi
echo "entrypoint: school api ${APP_VERSION:-unversioned}, listening on ${HOST}:${PORT}"
exec "$@"

🔒 ป้องกันการเผลอเปิดพอร์ตฐานข้อมูลสู่โลกภายนอก (Fail-Closed!)

4. การคุมลำดับการสตาร์ทด้วย healthcheck + depends_on: condition: service_healthy + --wait

  • คำว่าสถานะ Up ใน docker ps แปลแค่ว่า "โปรเซสในคอนเทนเนอร์เริ่มรันแล้ว" แต่ไม่ได้แปลว่า MySQL หรือ Node.js พร้อมรับการเชื่อมต่อแล้ว!
  • เราจึงต้องใส่ 3 ส่วนนี้ทำงานร่วมกัน:
    1. healthcheck ใน db: ใช้ ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1"] เพื่อเช็กว่า MySQL พร้อมรับคำสั่งหรือยัง
    2. depends_on: db: condition: service_healthy ใน api: สั่งให้ Compose รอจนกว่า db จะขึ้นสถานะ (healthy) ก่อน ถึงจะเริ่มสตาร์ท api (หมายเหตุ: depends_on คุมเฉพาะตอนสตาร์ทเท่านั้น ถ้าภายหลังเราสั่ง docker compose stop db ตัว api จะไม่ถูกหยุดตาม)
    3. healthcheck ใน api ต้องเช็กพาร์ทที่ต่อฐานข้อมูลจริง (Deep Healthcheck):
      ถ้าเช็กแค่ /api/health เวลาฐานข้อมูล db ล่ม ตัว api ก็ยังขึ้นว่า (healthy) หลอกเราอยู่ดี! ดังนั้นต้องเช็กที่ http://127.0.0.1:3000/api/students (หรือพาร์ทที่ดึงข้อมูลจริง เช่น /api/notices ในการบ้าน)
    4. docker compose up -d --wait: แฟล็ก --wait จะสั่งให้คำสั่งบน Terminal รอจนกว่าทุกบริการที่มี healthcheck จะขึ้นสถานะ (healthy) ครบทั้งหมดก่อน จึงจะคืนบรรทัดคำสั่งกลับมา

หัวข้อเปรียบเทียบ 1. Outer Proxy (Nginx บนเครื่อง VM) 2. Inner Stack Proxy (บริการ proxy ใน compose.yaml)
พอร์ตที่เปิดรับ 0.0.0.0:80 และ 0.0.0.0:443 (รับคนจากนอกเครื่อง) 127.0.0.2:8080:80 และ 127.0.0.2:8443:443 (รับเฉพาะจาก Outer Proxy ในเครื่องเดียวกัน)
ไฟล์ใบรับรอง TLS /etc/ssl/int134/vm.crt และ vm.key (ที่สร้างใน Class 5 — เบราว์เซอร์ของผู้ใช้จะเห็นใบรับรองใบนี้!) ./certs/tls.crt และ tls.key (Mount เข้าไปที่ /etc/ssl/school:ro เพื่อคุย HTTPS กับ Outer Proxy)
การเขียน proxy_pass ห้ามใส่ / ปิดท้ายเด็ดขาด!
• พอร์ต 80: proxy_pass http://127.0.0.2:8080;
• พอร์ต 443: proxy_pass https://127.0.0.2:8443;
(ถ้าเผลอใส่ / มันจะตัด /school/ ทิ้งตั้งแต่ข้างนอก พอไปถึง Stack Proxy ข้างในจะได้รับแค่ GET / แล้วตอบ 404 Not Found ทันที!) 		ต้องใส่ / และ /api/ ปิดท้าย!
• location /school/ ──► proxy_pass http://web/;
• location /school/api/ ──► proxy_pass http://api:3000/api/;
(เพราะตัวนี้คือ Proxy ด่านสุดท้ายก่อนถึง web และ api จึงต้องตัด /school/ ออก)
การทำ HTTP 308 Redirect ใน /etc/nginx/conf.d/http-default.conf ต้องเอา return 308 ใส่ไว้ใน location / { ... } เพื่อเปิดทางให้ location /school/ ส่งต่อ HTTP ไปให้พอร์ต 8080 ได้ (พร้อมแนบ proxy_set_header Host $host;) ใน listen 80; สั่ง return 308 https://$host$request_uri; เพื่อเป็นคนสั่งเด้งไป HTTPS
การบันทึก IP จริงของผู้ใช้ ส่งค่า proxy_set_header X-Real-IP $remote_addr; เข้าไปข้างใน หากไม่ตั้งค่าเพิ่ม ใน docker compose logs proxy จะเห็น IP ต้นทางเป็น 172.18.0.1 (IP ของ Docker Bridge) จึงต้องใส่ 2 บรรทัดนี้:
set_real_ip_from 172.16.0.0/12;
real_ip_header X-Real-IP;

3. 3 ข้อควรระวังสำคัญมากใน Class 10 (ออกสอบทั้งช้อยส์และปฏิบัติ!)

  1. ทำไมบริการ proxy ถึงต้อง Mount ทั้งโฟลเดอร์ ./proxy:/etc/nginx/conf.d:ro แทนที่จะ Mount แค่ไฟล์เดียว?
    • การ Mount ทับทั้งโฟลเดอร์ /etc/nginx/conf.d จะช่วย ซ่อนไฟล์ default.conf ดั้งเดิม ที่ติดมากับอิมเมจ nginx:1.30-alpine ทิ้งไปเลย
    • เวลาเราแก้ไขไฟล์บนเครื่อง Host ด้วยโปรแกรม vi ตัว vi จะสร้างไฟล์ใหม่ (Inode ใหม่) แล้วเปลี่ยนชื่อทับไฟล์เดิม ถ้าเรา Mount แค่ไฟล์เดียว คอนเทนเนอร์จะยังชี้ไปที่ Inode เก่า (แก้ไฟล์แล้วข้างในไม่อัปเดต!) แต่ถ้า Mount ทั้งโฟลเดอร์ พอแก้ไฟล์แล้วสั่ง docker compose exec proxy nginx -s reload ค่าใหม่จะทำงานทันที!
  2. การปิดประตูข้าง (Side Doors): เมื่อมีบริการ proxy เป็นประตูหน้าของ Stack แล้ว เราต้อง ลบบล็อก ports: ออกจากบริการ db, api, และ web ใน compose.yaml ทั้งหมด! ให้เหลือแค่บริการ proxy ตัวเดียวเท่านั้นที่มี ports: (8080:80 และ 8443:443)
  3. กับดัก Nginx จำ IP เก่าของคอนเทนเนอร์ (Stale Upstream DNS Cache):
    • ตอนที่เราลบ ports: ออกจาก web และ api แล้วสั่ง docker compose up -d ตัว Compose จะสร้างคอนเทนเนอร์ web และ api ใหม่ ทำให้มันอาจได้ IP Address ใหม่ในวงแลน school_default (บางครั้งสลับ IP กันเองด้วย!)
    • แต่เนื่องจากคอนเทนเนอร์ proxy ไม่ได้ถูกแก้ไขค่า มันจึงไม่ถูกรีสตาร์ท และธรรมชาติของ Nginx คือ แปลงชื่อ web กับ api เป็น IP แค่ครั้งเดียวตอนสตาร์ท แล้วจำ IP เก่าไว้ตลอด!
    • ดังนั้น หลังสร้างหรือ Recreate คอนเทนเนอร์ข้างหลังใหม่ ต้องสั่ง docker compose restart proxy เสมอ!
